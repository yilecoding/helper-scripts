# 百度网盘分享批量转存（baidu-share-dedupe）开发笔记

## 做什么

别人分享的文件夹里有一两千个文件，非会员在分享页一次最多转存 500 个，超了就报错。手动分批的话，要自己数到 500、
记住转到了哪儿，中途断了还分不清哪些已经存过，再转一遍又会多出一堆 `xxx(1).jpg`。

脚本在分享页右下角放一个面板，三步做完：

1. **选文件夹**：分享里的哪个文件夹 → 存到自己网盘的哪个文件夹（都能「浏览」着选）；
2. **扫描核对**：把两边的文件列表读全，按**文件名 + 大小**比对，算出已存在 / 待转存 / 要分几批；
3. **分批转存**：每批 500 个，转完一批确认都到了目标文件夹，再转下一批。

中途停了、关了页面、某批没到齐，重新点「扫描核对」再「开始转存」就接着做，已经在的会跳过。

这个脚本最早是为一个具体的分享链接写的（分享短链、来源和目标文件夹、预计文件数都写死在代码里），
收进仓库时改成了对任意分享链接可用。

## 怎么实现的

```
shareKey(location)          分享短链：/s/1xxx → xxx，/share/init?surl=xxx → xxx
shareInfo()                 shareid / 分享者 uk / bdstoken：yunData → locals → /api/gettemplatevariable
readShareDir(info, dir)     /share/list，dir 为 / 时用 root=1，100 一页
readDiskDir(dir)            /api/list，1000 一页，每次带不重复的 _t
compare(source, target)     按文件名 + 大小 → { missing, existing }，冲突就抛错
transfer(info, files, dir)  POST /share/transfer，fsidlist=[id,…]，path=目标文件夹
```

`Job.run()` 的循环：

```
重读目标 → compare → 没有缺的 → 完成
                   → 取前 500 个缺的 → transfer → 每 3 秒重读目标，这 500 个都在了 → 下一轮
                                                 └ 20 次（约 1 分钟）还不齐 → 停，提示重新扫描续跑
```

每一批之前都重读目标再核对，只信目标里实际有什么，不信「上一批接口返回成功」。
这样续跑不需要存任何进度：进度就是目标文件夹本身。

界面在 shadow DOM 里，不受分享页样式影响。存在 GM 存储里的只有一项：上次扫描成功的目标文件夹（`lastTarget`）。

## 用到的接口

都是网页版自己在用的同源接口，带浏览器里的登录 Cookie 请求，不经过任何第三方。
参数来自原脚本（在真实分享页上用过）和网页版的请求；标「推断」的没有在真实页面上验证过。

| 接口 | 用途 | 关键参数 | 把握 |
|---|---|---|---|
| `GET /share/list` | 列分享里的文件夹 | `shareid` `uk` `shorturl` `sekey` `dir` `page` `num=100` | `dir` 方式原脚本用过；`root=1` 列最外层是**推断** |
| `GET /api/list` | 列自己网盘的文件夹 | `dir` `page` `num=1000` | 原脚本用过 |
| `POST /share/transfer` | 转存 | query：`shareid` `from=uk` `bdstoken`；表单：`fsidlist` `path` | 原脚本用过 |
| `GET /api/gettemplatevariable` | 页面上没有 bdstoken 时取 | `fields=["bdstoken"]` | 原脚本用过 |

- `sekey` 取 Cookie `BDCLND`（输过提取码后百度写的），没有时取页面变量 `sekey`。
- 分享信息原脚本只读 `window.yunData`；新版分享页可能放在 `window.locals`（对象或带 `get()`），兼容写法是**推断**。
- 分享页地址里记当前浏览路径的两种写法（`#list/path=` 和 `?path=`）是**推断**，读不到就退回「最外层只有一个文件夹就选它」。

## 关键的坑

标注「实测」的是原脚本在真实分享页上遇到过的，或测试里复现过的；「推断」的是按机制推出来的。

1. **fs_id 超过 JS 安全整数（实测）。** fs_id 是十几到二十位的整数，`JSON.parse` 会把末几位变成 0，
   转存时指向别的文件或报文件不存在。解析前用正则把 `"fs_id": 123…` 改成字符串，之后全程不经过 `Number`。
   测试里假网盘的 fs_id 从 2^53 + 1 起编号，并在 JSON 原文里写成裸整数，丢精度的话转存会被拒。
2. **转存后列表返回缓存的旧页（实测）。** 转存成功后反复请求同样的 `/api/list` URL，可能一直拿到转存前的结果，
   核对永远等不到新文件。每次请求带一个不重复的 `_t`。测试里假网盘可以开「同样的 query 回同样的结果」，
   去掉 `_t` 那个用例就会超时失败。
3. **接口返回成功但文件晚到或没到齐（推断，原脚本就有这一步核对）。** 所以每批之后要核对，到不齐就停，而不是接着发下一批。
4. **同名不同大小时停下，不转（推断）。** 目标里已有同名文件时百度会把新的改名成 `xxx(1).jpg` 存进去，
   悄悄多出一份比漏一份更难发现。同名但大小不同、同名的是文件夹、分享里自己有重名，都停下交给人判断。
5. **翻页时出现重复 fs_id 就停（推断）。** 说明分页错位了（接口缓存或排序不稳定），继续读可能有文件被挤到页外漏掉。
6. **分享最外层的「上一级」（推断）。** 最外层条目的 `path` 是分享者网盘里的完整路径（比如 `/资料/2024/照片`），
   从路径往上截出来的 `/资料/2024` 不在分享范围里。选择器的「上一级」靠面包屑栈退回，不截路径。
7. **停止不打断请求。** 已经发出去的那批转存没法撤回，点停止后等它返回、在下一步开始前停下；停下不算出错，不标红。

## 已知限制

- **不转子文件夹。** 来源里的子文件夹会跳过并列出名字。整个文件夹转过去没法按文件去重，里面的文件也算进 500 个的上限。
  需要的话点「浏览」选进子文件夹，单独再转一次。
- **只按文件名 + 大小判断是否已存在**，不比内容（网页接口拿不到分享文件的 md5）。
- **每批固定 500 个。** 会员单次上限更高，但脚本没区分，会员用也只是批数多一些。
- **不会自动新建目标文件夹。** 不存在时提示先在网盘里建好。
- 百度触发验证码、提取码过期、分享被取消时，脚本只显示接口返回的错误，处理好后重新扫描即可。
- 网页版接口随时可能改，参数和返回格式都没有官方文档。

## 怎么跑测试

```bash
NODE_PATH=/path/to/node_modules node baidu-share-dedupe/test/run.cjs
```

`NODE_PATH` 指向任意一个装了 `playwright` 的 `node_modules`（本仓库不带依赖）。
不访问外网，也不碰真实网盘：`https://pan.baidu.com` 下的请求全部用 `page.route` 接住，
分享页回 `fixtures/share.html`（把 `yunData` 填进去），接口由 `test/fake-pan.cjs` 里的假网盘回答。
假网盘有分享方和自己网盘两棵文件树，能模拟单次转存上限、转存后文件晚到（`lag`）、返回成功但少存几个（`drop`）、
列表缓存（`cache`）和任意接口返回指定 errno（`fail()`）。转存后的等待用 `page.clock` 快进，不真等。

覆盖：只在分享页出现、收起 / 隐藏、分享列表翻页、最外层 `root=1`、`sekey`、bdstoken 兜底与复用、
核对（已存在跳过、目标翻页、同名不同大小、同名文件夹、分享重名、目标没填）、分批 500 / 500 / 203、
fs_id 不丢精度、晚到、没到齐后续跑、转存报错、列表缓存、目标不存在、停止与续跑、改文件夹后要重新核对、
默认值（地址里的路径、唯一的顶层文件夹、记住目标）、子文件夹跳过、至少文件数、文件夹选择器、步骤条与批次显示。

harness 和真实 Tampermonkey 的差异，影响到的地方：

- 没有沙箱，`unsafeWindow === window`。真实环境里 `yunData` / `locals` 是页面的变量，要经过 `unsafeWindow` 才读得到，
  这一点测试测不出来。
- GM 存储按源存在 localStorage，`browser.newPage()` 每次是新 context，测「记住目标」时用 `values` 预置。
